2. BACKEND APPLICATION ARCHITECTURE
--------------------------------------

The Express.js backend uses a layered architecture to separate
concerns and keep code maintainable.

  Route Handler (routes/)
       |
       | -- Validates request body using Zod
       | -- Checks JWT via auth middleware
       v
  Service Layer (services/)
       |
       | -- Contains all business logic
       | -- Checks Redis cache before querying DB
       | -- Writes to Redis cache after DB queries
       v
  Data Layer (lib/prisma.ts)
       |
       | -- Prisma Client sends SQL to Supabase PostgreSQL
       v
  Supabase PostgreSQL Database

Folder structure of the backend:

  apps/backend/src/
    routes/
      auth.routes.ts         Login, logout, token refresh
      centres.routes.ts      CRUD for centres
      workers.routes.ts      CRUD for workers and assignments
      stock.routes.ts        Stock item management
      services.routes.ts     Service event logging and retrieval
      notices.routes.ts      Send and receive notices
      reports.routes.ts      Daily and weekly summaries

    middleware/
      authenticate.ts        Validates JWT, checks Redis session store
      authorise.ts           Role guard (owner-only or worker-only routes)
      validate.ts            Zod request body validation wrapper
      errorHandler.ts        Global error handler (formats error responses)

    services/
      auth.service.ts        Token generation, hashing, session management
      centre.service.ts      Centre business logic
      worker.service.ts      Worker and assignment logic
      stock.service.ts       Stock management logic
      service.service.ts     Service event logic and totals
      notice.service.ts      Notice creation and push dispatch
      report.service.ts      Aggregation queries for reports

    lib/
      prisma.ts              Singleton Prisma Client instance
      redis.ts               Upstash Redis client instance
      push.ts                Expo push notification sender helper

    utils/
      token.ts               JWT sign and verify helpers
      format.ts              Currency formatting, date helpers
      constants.ts           App-wide constants (TTL values, limits)

  prisma/
    schema.prisma            Database schema (single source of truth)
    migrations/              Auto-generated SQL migrations


3. AUTHENTICATION FLOW
------------------------

OWNER LOGIN
  Step 1: Mobile sends POST /auth/owner/login
          Body: { email, password }

  Step 2: Backend finds user in PostgreSQL by email
          Compares password against bcrypt hash

  Step 3: On success, backend generates a JWT:
          Payload: { userId, role: "owner", iat, exp }
          Signed with the backend's JWT_SECRET env variable
          Expiry: 7 days

  Step 4: JWT stored in Upstash Redis:
          Key  : session:<userId>:<jti>
          Value: "valid"
          TTL  : 7 days (same as token expiry)

  Step 5: JWT returned to mobile app in response body
          Mobile stores it in Expo SecureStore

WORKER LOGIN (Centre-ID based)
  Step 1: Mobile sends POST /auth/worker/login
          Body: { centreId }

  Step 2: Backend queries centres table for matching centre_id
          Checks worker_centre_assignments for an active assignment
          at that centre

  Step 3: On success, backend generates a JWT:
          Payload: { userId, role: "worker", centreId, iat, exp }
          Expiry: 12 hours (shorter for workers)

  Step 4: JWT stored in Redis:
          Key  : session:<userId>:<jti>
          Value: "valid"
          TTL  : 12 hours

  Step 5: JWT returned to mobile and stored in Expo SecureStore

JWT VALIDATION (every protected request)
  Step 1: Mobile sends request with header:
          Authorization: Bearer <jwt_token>

  Step 2: authenticate middleware:
          a. Verifies JWT signature using JWT_SECRET
          b. Checks token has not expired (exp claim)
          c. Looks up Redis key session:<userId>:<jti>
          d. If key missing from Redis: token is blacklisted or expired
             -- return 401 Unauthorised

  Step 3: Attaches decoded user payload to request object
          Next middleware or route handler runs

LOGOUT
  Step 1: Mobile sends POST /auth/logout with JWT in header

  Step 2: Backend decodes the JWT to get the jti (token ID)

  Step 3: Deletes the session key from Redis:
          DEL session:<userId>:<jti>
          Token is now permanently invalid even if not expired

  Step 4: Returns 200 OK. Mobile clears SecureStore.

ROLE GUARD
  Routes under /owner/* require JWT payload role === "owner"
  Routes under /worker/* require JWT payload role === "worker"
  The authorise middleware checks this after JWT validation


4. REDIS CACHING STRATEGY
---------------------------

Upstash Redis is used for two distinct purposes:

PURPOSE 1: Session Storage (JWT management)
  Pattern  : session:<userId>:<jti>
  Value    : "valid"
  TTL      : Matches JWT expiry (7 days owner, 12 hrs worker)
  On logout: Key deleted immediately (token blacklisted)
  On expiry: Redis auto-deletes the key (no cleanup needed)

PURPOSE 2: API Response Caching (performance)
  The Render free tier spins down after 15 minutes of inactivity.
  The first request after wakeup may be slow (5-10 seconds).
  Redis cache ensures subsequent requests are fast.

  Cached data       Key pattern              TTL
  ----------------  -----------------------  --------
  Owner centres     cache:centres:<ownerId>  5 minutes
  Worker list       cache:workers:<ownerId>  5 minutes
  Centre workers    cache:cworkers:<centId>  5 minutes
  Stock list        cache:stock:<centreId>   2 minutes
  Daily report      cache:report:d:<centId>  10 minutes
  Weekly report     cache:report:w:<centId>  30 minutes

  Cache invalidation rules:
    - Whenever a write operation modifies data (INSERT, UPDATE, DELETE),
      the relevant cache key is deleted so the next read fetches fresh
      data from PostgreSQL.
    - Example: worker adds a stock item -> DELETE cache:stock:<centreId>
               next GET /stock fetches from DB and caches the result again


5. DATABASE DESIGN
--------------------

The PostgreSQL schema is defined in prisma/schema.prisma and managed
through Prisma migrations. All tables are in the Supabase PostgreSQL
database. Supabase is used as a plain PostgreSQL host only.

Entity Relationships:

  users  <---(owner_id)---  centres
  users  <---  worker_centre_assignments  --->  centres
  centres  --->  stock_items          (one to many)
  centres  --->  service_events       (one to many)
  centres  --->  notices              (one to many)
  users    --->  service_events       (one worker to many events)
  users    --->  notices              (one owner to many notices sent)
  notices  --->  notice_reads         (one notice to many read records)
  users    --->  expo_push_tokens     (one user to many device tokens)


TABLE: users
Purpose: All application users (owners and workers).

  Column           Type          Notes
  --------------   -----------   -----------------------------------------
  id               UUID          Primary key. Auto-generated.
  email            TEXT          Unique. Owner email. Nullable for workers.
  phone            TEXT          Unique. Worker phone number.
  full_name        TEXT          Required.
  nim              TEXT          Unique. Worker employee number.
  password_hash    TEXT          bcrypt hash. Nullable for workers
                                 (workers log in by Centre ID, not password).
  role             TEXT          Required. Values: "owner" or "worker".
  is_active        BOOLEAN       Default true. Soft delete flag.
  created_at       TIMESTAMPTZ   Auto-set on creation.
  updated_at       TIMESTAMPTZ   Auto-set on each update.

  Prisma schema definition:
    model User {
      id            String    @id @default(uuid())
      email         String?   @unique
      phone         String?   @unique
      fullName      String
      nim           String?   @unique
      passwordHash  String?
      role          String
      isActive      Boolean   @default(true)
      createdAt     DateTime  @default(now())
      updatedAt     DateTime  @updatedAt

      ownedCentres        Centre[]
      serviceEvents       ServiceEvent[]
      sentNotices         Notice[]
      noticeReads         NoticeRead[]
      pushTokens          ExpoPushToken[]
      centreAssignments   WorkerCentreAssignment[]
    }


TABLE: centres
Purpose: Each physical stationery service centre.

  Column           Type          Notes
  --------------   -----------   -----------------------------------------
  id               UUID          Primary key.
  centre_no        TEXT          Unique. Business code e.g. STN001.
  centre_id        TEXT          Unique. Worker login ID e.g. CENTRE-ARU-001.
  name             TEXT          Required. Display name.
  location         TEXT          Required. E.g. "Arusha University".
  owner_id         UUID          Foreign key to users. Required.
  is_active        BOOLEAN       Default true. Soft delete.
  created_at       TIMESTAMPTZ   Auto-set.
  updated_at       TIMESTAMPTZ   Auto-set.

  Prisma schema definition:
    model Centre {
      id         String    @id @default(uuid())
      centreNo   String    @unique
      centreId   String    @unique
      name       String
      location   String
      ownerId    String
      isActive   Boolean   @default(true)
      createdAt  DateTime  @default(now())
      updatedAt  DateTime  @updatedAt

      owner          User                     @relation(fields: [ownerId], references: [id])
      stockItems     StockItem[]
      serviceEvents  ServiceEvent[]
      notices        Notice[]
      assignments    WorkerCentreAssignment[]
    }


TABLE: worker_centre_assignments
Purpose: Maps workers to their assigned centre (many-to-many link).

  Column            Type          Notes
  ---------------   -----------   -----------------------------------------
  id                UUID          Primary key.
  worker_id         UUID          Foreign key to users.
  centre_id         UUID          Foreign key to centres.
  is_active         BOOLEAN       Default true. Current assignment flag.
  assigned_at       TIMESTAMPTZ   Auto-set when assignment is made.
  transferred_from  UUID          Nullable. Previous centre if transferred.

  Prisma schema definition:
    model WorkerCentreAssignment {
      id              String    @id @default(uuid())
      workerId        String
      centreId        String
      isActive        Boolean   @default(true)
      assignedAt      DateTime  @default(now())
      transferredFrom String?

      worker  User    @relation(fields: [workerId], references: [id])
      centre  Centre  @relation(fields: [centreId], references: [id])
    }


TABLE: stock_items
Purpose: Inventory stock items per centre.

  Column                Type          Notes
  --------------------  -----------   -----------------------------------------
  id                    UUID          Primary key.
  centre_id             UUID          Foreign key to centres.
  registered_by         UUID          Foreign key to users (worker).
  item_name             TEXT          Required. E.g. "Ink Pens".
  quantity              DECIMAL       Required. Must be >= 0.
  unit                  TEXT          Required. Values: "pcs" or "boxes".
  net_stock_price_tshs  DECIMAL       Required. Must be >= 0.
  notes                 TEXT          Nullable.
  created_at            TIMESTAMPTZ   Auto-set.
  updated_at            TIMESTAMPTZ   Auto-set.

  Prisma schema definition:
    model StockItem {
      id                 String    @id @default(uuid())
      centreId           String
      registeredBy       String?
      itemName           String
      quantity           Decimal
      unit               String
      netStockPriceTshs  Decimal
      notes              String?
      createdAt          DateTime  @default(now())
      updatedAt          DateTime  @updatedAt

      centre  Centre  @relation(fields: [centreId], references: [id])
      worker  User?   @relation(fields: [registeredBy], references: [id])
    }


TABLE: service_events
Purpose: Each customer service transaction at a centre.

  Column                Type          Notes
  --------------------  -----------   -----------------------------------------
  id                    UUID          Primary key.
  centre_id             UUID          Foreign key to centres.
  worker_id             UUID          Foreign key to users (worker).
  service_type          TEXT          photocopy / printing / lamination /
                                      scanning / designing / other
  service_subtype       TEXT          Nullable. "black_and_white" or "colour".
  category              TEXT          Nullable.
  pages                 INTEGER       Nullable. Must be >= 1.
  price_per_page_tshs   DECIMAL       Nullable. Must be >= 0.
  total_amount_tshs     DECIMAL       Required. Computed: pages x price_per_page.
  customer_note         TEXT          Nullable.
  created_at            TIMESTAMPTZ   Auto-set.

  Prisma schema definition:
    model ServiceEvent {
      id                 String    @id @default(uuid())
      centreId           String
      workerId           String
      serviceType        String
      serviceSubtype     String?
      category           String?
      pages              Int?
      pricePerPageTshs   Decimal?
      totalAmountTshs    Decimal
      customerNote       String?
      createdAt          DateTime  @default(now())

      centre  Centre  @relation(fields: [centreId], references: [id])
      worker  User    @relation(fields: [workerId], references: [id])
    }


TABLE: notices
Purpose: Messages and instructions sent by owner to workers.

  Column       Type          Notes
  ----------   -----------   -----------------------------------------
  id           UUID          Primary key.
  sender_id    UUID          Foreign key to users (owner).
  centre_id    UUID          Foreign key to centres.
  title        TEXT          Required.
  body         TEXT          Required. Full message content.
  priority     TEXT          Default "normal". Values: low, normal, urgent.
  created_at   TIMESTAMPTZ   Auto-set.

  Prisma schema definition:
    model Notice {
      id         String    @id @default(uuid())
      senderId   String
      centreId   String
      title      String
      body       String
      priority   String    @default("normal")
      createdAt  DateTime  @default(now())

      sender   User         @relation(fields: [senderId], references: [id])
      centre   Centre       @relation(fields: [centreId], references: [id])
      reads    NoticeRead[]
    }


TABLE: notice_reads
Purpose: Tracks which workers have read which notices.

  Column      Type          Notes
  ---------   -----------   -----------------------------------------
  id          UUID          Primary key.
  notice_id   UUID          Foreign key to notices.
  worker_id   UUID          Foreign key to users.
  read_at     TIMESTAMPTZ   Auto-set when worker opens the notice.

  Unique constraint: one record per notice + worker combination.

  Prisma schema definition:
    model NoticeRead {
      id        String   @id @default(uuid())
      noticeId  String
      workerId  String
      readAt    DateTime @default(now())

      notice  Notice  @relation(fields: [noticeId], references: [id])
      worker  User    @relation(fields: [workerId], references: [id])

      @@unique([noticeId, workerId])
    }


TABLE: expo_push_tokens
Purpose: Device push tokens for delivering push notifications.

  Column      Type          Notes
  ---------   -----------   -----------------------------------------
  id          UUID          Primary key.
  user_id     UUID          Foreign key to users.
  token       TEXT          Unique. Expo push token string.
  platform    TEXT          "ios" or "android".
  updated_at  TIMESTAMPTZ   Updated on each login to keep token current.

  Prisma schema definition:
    model ExpoPushToken {
      id        String   @id @default(uuid())
      userId    String
      token     String   @unique
      platform  String?
      updatedAt DateTime @updatedAt

      user  User  @relation(fields: [userId], references: [id])
    }


6. API ENDPOINT REFERENCE
---------------------------

All endpoints are prefixed with /api/v1

AUTH ROUTES (no JWT required)
  POST  /api/v1/auth/owner/register    Register new owner account
  POST  /api/v1/auth/owner/login       Owner email + password login
  POST  /api/v1/auth/worker/login      Worker Centre-ID login
  POST  /api/v1/auth/logout            Invalidate session in Redis

CENTRE ROUTES (owner JWT required)
  GET   /api/v1/centres                List all centres for logged-in owner
  POST  /api/v1/centres                Create a new centre
  GET   /api/v1/centres/:id            Get single centre details
  PATCH /api/v1/centres/:id            Update centre details
  DELETE /api/v1/centres/:id           Deactivate a centre (soft delete)

WORKER ROUTES (owner JWT required)
  GET   /api/v1/workers                List all workers for owner's centres
  POST  /api/v1/workers                Register a new worker
  GET   /api/v1/workers/:id            Get single worker details
  PATCH /api/v1/workers/:id            Update worker profile
  POST  /api/v1/workers/:id/assign     Assign worker to a centre
  POST  /api/v1/workers/:id/transfer   Transfer worker to another centre
  DELETE /api/v1/workers/:id           Deactivate a worker

STOCK ROUTES
  GET   /api/v1/stock                  Worker: list stock at their centre
                                       Owner: list stock across all centres
  POST  /api/v1/stock                  Worker: register new stock item
  PATCH /api/v1/stock/:id              Worker: update stock item
  DELETE /api/v1/stock/:id             Worker: delete stock item

SERVICE EVENT ROUTES
  GET   /api/v1/services               Worker: today's events at their centre
                                       Owner: all events (with filters)
  POST  /api/v1/services               Worker: log a new service event
  PATCH /api/v1/services/:id           Worker: edit event (within 60 min)
  DELETE /api/v1/services/:id          Worker: delete event (within 60 min)

NOTICE ROUTES
  GET   /api/v1/notices                Worker: notices for their centre
                                       Owner: notices they have sent
  POST  /api/v1/notices                Owner: send a new notice
  POST  /api/v1/notices/:id/read       Worker: mark notice as read

REPORT ROUTES (owner JWT required)
  GET   /api/v1/reports/daily          Daily summary per centre
  GET   /api/v1/reports/weekly         Weekly summary per centre


7. STANDARD API RESPONSE FORMAT
---------------------------------

All API responses follow this consistent JSON structure:

  Success response:
    {
      "success": true,
      "data": { ... }         (or an array for list endpoints)
    }

  Error response:
    {
      "success": false,
      "error": {
        "code": "VALIDATION_ERROR",
        "message": "Centre number is already taken.",
        "details": [ ... ]    (optional field-level errors for validation)
      }
    }

  HTTP status codes used:
    200  OK                   Successful GET, PATCH, DELETE
    201  Created              Successful POST (new resource created)
    400  Bad Request          Validation error (Zod schema failed)
    401  Unauthorised         Missing or invalid JWT
    403  Forbidden            Valid JWT but wrong role for this route
    404  Not Found            Resource does not exist
    409  Conflict             Duplicate value (centre_no, NIM, email)
    500  Internal Server Error Unexpected backend error


8. PUSH NOTIFICATION FLOW
---------------------------

When the owner sends a notice, the backend dispatches push
notifications to all active workers at the target centre.

  Step 1 : Owner sends POST /api/v1/notices
           Body: { centreId, title, body, priority }

  Step 2 : notice.service.ts inserts the notice record into PostgreSQL

  Step 3 : notice.service.ts queries expo_push_tokens for all workers
           assigned to the target centreId

  Step 4 : push.ts sends a single batched request to the Expo Push API:
           POST https://exp.host/--/api/v2/push/send
           Body: array of push message objects (one per worker token)

  Step 5 : Expo's servers forward to:
             FCM  for Android devices
             APNs for iOS devices

  Step 6 : Worker device receives a push notification showing the
           notice title. Tapping it opens the Notice Detail screen.

  Worker saves their push token:
    On every login, the worker app calls Expo to get the device push token
    and sends it to POST /api/v1/push-token. The backend upserts the token
    in expo_push_tokens (update if exists, insert if new). This keeps
    tokens current if the OS refreshes them.


9. ENVIRONMENT VARIABLES
--------------------------

Backend (.env file -- never committed to Git):

  DATABASE_URL          Full Supabase PostgreSQL connection string
                        Format: postgresql://user:pass@host:5432/dbname
  DIRECT_URL            Direct connection URL (for Prisma migrations)
  REDIS_URL             Upstash Redis connection string
                        Format: rediss://:<password>@<host>:<port>
  JWT_SECRET            Long random string for signing JWTs
                        Generate with: openssl rand -hex 64
  JWT_OWNER_EXPIRY      Token expiry for owners. Example: 7d
  JWT_WORKER_EXPIRY     Token expiry for workers. Example: 12h
  PORT                  Port for the Express server. Default: 3000
  NODE_ENV              "development" or "production"

Mobile (apps/mobile/.env.local -- never committed to Git):

  EXPO_PUBLIC_API_URL           Backend API base URL on Render
                                Example: https://smss-api.onrender.com/api/v1
  EXPO_PUBLIC_APP_NAME          SMSS

Render deployment environment variables:
  All backend .env values are added in the Render dashboard under
  Environment Variables for the web service. They are not stored
  in any file in the repository.


10. OFFLINE STRATEGY
----------------------

Feature                Offline Strategy
---------------------  ---------------------------------------------------------
Stock entries          Queued in Expo SQLite on device.
                       Synced to backend API when connection is restored.
Service events         Queued in Expo SQLite. Batch-synced on reconnect.
Notices inbox          Cached by React Query. Last-fetched notices visible
                       without connection.
Auth session           JWT stored in Expo SecureStore. Remains valid for
                       the session duration without a network call.
                       (Backend Redis check happens only on API requests.)
